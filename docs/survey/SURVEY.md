# Native-port survey — USA 1.1

**Verdict: conditional GO for the native architecture; NO-GO for compiling the existing C unchanged and merely replacing SDK link symbols.** The remaining matching work is small relative to the ABI, renderer, overlay and scheduling work. A Konami-logo boot proves only that narrow path.

## Scope and evidence

Inspected reference commit `d9e28f8315c7938117224f21516786d9d149a145`, read-only, on 2026-10-07. All decomp links below pin that commit. **All can be resident native modules after per-overlay namespacing**, preserving shared BODYPROG/SDK symbols and map defines. Generate prefixes from each overlay's owned symbols, including included shared definitions, and export `OverlayDescriptor { id, header, entry_points, initial_state/reset }`. Replace the engine's fixed header symbol with the active descriptor. This survey has not compiled that scheme; duplicate definitions prove the need, not that all link issues are solved.

Native “load” should drain/reconcile pending work, activate the descriptor at the original completion point, restore that overlay's initial mutable data/BSS, and load assets normally. Returning to a resident map must not retain state that original overlay replacement erased. Encrypted machine code is never executed/copied into host executable memory; import only needed data tables/metadata. Keep a queue-completion transition even for cached/instant reads, respecting original state-machine ordering. Do not substitute immediate reentrant callbacks or skip initialization.

## Ranked risk list

1. **64-bit ABI and disk/runtime separation — highest, immediate.** Pointer-sized file slots, LP64 scalars, packed/aliasing tricks and hard-address data overlap can fail silently after a Windows logo boot. Require fixture decode/layout checks on x64 and arm64, then model/collision/DMS round trips with original IDs.
2. **GPU/GTE fidelity and smooth presentation — high.** Inline COP2 state, OT order, VRAM feedback and already-projected geometry are far broader than a GPU API stub. Require a real map, fog/blends, item TMD and framebuffer-effect comparisons before accepting the 60-fps design.
3. **Whole-game overlay integration — high.** Namespace every map-owned symbol and preserve load/reset lifecycle. Require transitions/re-entry across maps and screen overlays, proving callback/data identity and no stale native overlay state.
4. **Audio/video clocks and codecs — high.** XA, VAG/SPU and KDT need different backends; MDEC/STR is not a host-video API call. Require one XA bank, one looping VAB/KDT track and one movie with skip/offset/end/resume checks.
5. **Timing/input determinism and touch completeness — medium-high.** Thirty-Hz gameplay, sixty-Hz menus, vblank callbacks and per-update windows must survive higher refresh presentation. Require same-input replays at multiple host refresh rates plus every interaction type in input_map.md.
6. **Remaining C/RODATA work and importer hardening — medium.** Only one active missing function, but 78 raw blocks include unknown/matching-only data and pointer-bearing tables. Require importer bounds/identity checks and native reconstruction of consumed blocks; retain GPL notices when copying reference code.

## Go/no-go opinion

**GO to a bounded Windows native prototype using the C logic + Rust shell + explicit PsyQ-compatible services, with the ABI/overlay/timing changes above. NO-GO to treating PLAN.md's architecture as “unchanged C + thin stubs,” or promising whole-game 60-fps interpolation from the boot milestone.** Keep original logic schedules and a faithful renderer first; prove native loading of one map, an overlay transition, collision/model/DMS layouts on arm64, input replay and an audiovisual sample before expanding Phase 2. Those checks could upgrade this to an unconditional engineering go; failure to isolate serialized pointers or obtain deterministic stepping would change the verdict to no-go for this approach.
